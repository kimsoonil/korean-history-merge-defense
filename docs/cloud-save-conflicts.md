# 버전 기반 클라우드 저장과 복원

## 변경 범위

`game_saves`의 기존 `(user_id, storage_key)`와 문자열 value 형식, 게임 내부 저장 버전, Google/Apple 로그인은 유지한다. 기존 행은 revision 1로 이관한다. 새 저장은 `save_game_version` RPC에 읽었던 revision과 예상 user_id를 전송한다. 서버는 인증 계정을 검증하고 계정/키 단위 트랜잭션 잠금 후 revision이 일치할 때만 저장한다. 없는 행은 revision 0이다. 삭제는 tombstone으로 남겨 오래된 기기의 부활 저장을 거부한다.

충돌 시 서버 현재 행은 바꾸지 않고 제출 데이터를 `game_save_history`에 보존한다. 성공 시 이전 서버 행과 새 기록을 보존한다. 클라이언트도 양쪽 사본을 계정별 별도 로컬 영역에 보존하고 해당 키 전송을 차단한다. 저장 기준 버전, 미전송 값 및 차단 상태는 재시작 후에도 유지한다. 복원은 새로 읽은 서버 버전으로 다시 CAS를 수행하므로 복원 도중 다른 기기가 저장해도 무조건 덮어쓰지 않는다.

## 사용자 복원

로그인 후 우측 하단의 **클라우드 저장 복원 / 저장 충돌·백업 확인**을 연다. 복원 화면에서는 게임 컴포넌트를 내려 자동 저장과 전투 진행을 정지한다. 현재 기기, 현재 서버, 기기 백업 및 최근 서버 이력 200개를 비교한다. 항목 키·버전·보존 시각, 가능한 경우 닉네임·레벨·장·스테이지·라운드·게임 저장 시각을 표시하며 원본도 펼칠 수 있다. 기기 현재 행의 시각은 실제 저장 시각이 아니라 확인 시각으로 명시한다. 기존 `:local-backup:` 기록도 복원 목록에 포함한다.

기록 선택 후 별도 확정 버튼으로 복원한다. 복원 직전 기기 기록도 백업하며 성공 후 새로고침한다. 서버 연결이 없으면 기록을 확인할 수 있으나 서버 복원 확정은 실패하고 원본은 유지된다. 충돌을 미해결 상태로 게임을 계속하면 해당 항목은 기기에만 저장된다.

저장 단위는 기존과 같은 **키 단위**다. 프로필과 전투 등을 계정 전체의 한 시점으로 원자적으로 되돌리는 기능은 아니다. 여러 키를 복원하려면 각 항목을 선택한다. 진행도를 자동 병합하지 않으며 타임스탬프의 대소로 승자를 결정하지 않는다. 로컬 저장소를 지우거나 기기를 분실하기 전 서버에 도달하지 못한 오프라인 데이터까지 서버가 보호할 수는 없다.

## 오프라인·계정 전환

초기 서버 조회가 실패해도 로컬 게임을 열고 지속성 큐를 만든다. 온라인 이벤트 및 3초 재시도로 미전송 데이터를 보낸다. 서버 조회 없이 생성된 키는 revision 0으로 전송하여 기존 서버 값이 있다면 충돌로 보존한다. 게스트는 클라우드 큐와 복원 UI를 사용하지 않는다. 계정 전환/언마운트 시 큐를 즉시 닫고 타이머를 취소하며, 이미 시작한 응답은 로컬에 적용하지 않는다. RPC의 예상 계정 검증으로 토큰이 바뀐 뒤 이전 계정 데이터가 새 계정에 들어가는 것도 차단한다.

## 적용 순서 — 운영 적용 미실시

1. 운영 DB 백업 후 스테이징에 `20261020000000_cloud_save_versions.sql`을 적용하고 아래 검증과 실제 Google/Apple 두 기기 검증을 수행한다.
2. 새 클라이언트를 빌드/배포한다. 웹·Android·iOS 릴리스는 각각 별도 작업이다.
3. DB 마이그레이션은 새 클라이언트보다 먼저 적용해야 한다. 마이그레이션과 새 클라이언트 사이에는 이전 앱의 직접 저장이 거부된다. 이전 앱은 로컬 플레이만 가능하므로 앱 업데이트 안내 및 배포 시간을 조율해야 한다. 이전 앱을 허용하는 정책을 다시 열면 CAS를 우회하므로 금지한다.
4. 운영 Supabase 마이그레이션, 웹 배포, 앱 스토어 제출은 이 PR에서 실행하지 않았다. 운영의 최신 소스/스키마와 먼저 비교한다.

RPC가 누락되거나 서버 오류가 나면 무조건 upsert로 되돌리지 않고 로컬 미전송 데이터를 유지한다. 롤백 시에도 구버전 직접 쓰기 권한을 다시 열지 않는다. 저장 이력은 자동 정리하지 않으며 무제한 증가할 수 있다. 운영자는 저장 빈도·용량을 모니터링하고 별도 보존 정책을 결정해야 한다.

## 다른 작업과의 경계

main에서 분기한 독립 PR이다. 기존 테스트 안정화, 출시 명칭 변경 PR #1, 계정 삭제 UI/API 작업을 포함하지 않는다. 계정 삭제의 서버 측 auth.users 삭제는 두 저장 테이블에 cascade되므로 기존 삭제 경로를 유지한다. 인증 사용자에게 직접 game_saves DELETE를 허용하는 구현은 새 구조와 호환되지 않으며, 게임 내 저장 삭제는 RPC tombstone을 써야 한다. 계정 삭제 작업에서는 서버 계정 삭제와 함께 기기의 `khmd-account-v1:user:<id>:` 및 `khmd-cloud-v2:<id>`, `khmd-cloud-backups-v2:<id>`도 정리해야 한다. 로그아웃은 오프라인 미전송 데이터를 보존하기 위해 이 키들을 지우지 않는다.

- 선택적 PostgreSQL 실행 테스트: 임시 디렉터리에 `@electric-sql/pglite` 설치 후 `PGLITE_MODULE=/absolute/path/to/node_modules/@electric-sql/pglite/dist/index.js node --test tests/cloud-save-postgres.test.mjs`. 프로젝트 의존성은 변경하지 않는다.
